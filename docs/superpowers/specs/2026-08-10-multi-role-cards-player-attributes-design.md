# 多角色卡剧本与剧本级玩家属性设计

## 背景与目标

现有角色卡已经独立于剧本保存，但一个剧本只能通过 `works.card_id` 引用一张角色卡，玩家初始属性也仍然位于角色卡的 `initial_state.attributes` 中。本次调整解决两个问题：

1. 玩家属性属于玩家在某个剧本中的设定，应在剧本设置中编辑，而不是在角色卡中编辑。
2. 一个剧本可以按顺序引用多张角色卡，所有被引用角色卡都会在该剧本新开的会话中生效。

本次继续遵守上一版约束：不增加“初始数值关系”编辑区；已有旧角色卡中的隐藏 `initial_state` 数据不因表单保存而丢失；已开始的旧会话不因角色卡或剧本设置更新而改变。

## 已确认的产品语义

- 一个剧本有一套剧本级玩家初始属性。
- 一个剧本拥有有序角色卡列表；角色卡在列表中的顺序用于 UI 展示和 AI 上下文组装。
- 同一角色卡可以被多个剧本引用；同一剧本内不重复引用同一张卡。
- 角色卡编辑只改变角色卡资源。被多个剧本引用时，界面列出受影响剧本，并明确说明只影响这些剧本之后新开的会话。
- 删除被任一剧本引用的角色卡仍然禁止，并展示所有引用剧本。
- 剧本编辑只改变自己的角色卡列表和玩家属性，不修改角色卡内容。
- 空角色卡列表表示该剧本不使用角色卡；旧 API 的 `card_id: null` 继续表示空列表。

## 方案选择

### 方案 A：规范化剧本—角色卡关联表（采用）

新增 `work_cards(work_id, card_id, position)`，以 `position` 保存顺序；剧本自身新增 `player_attributes` JSON。保留旧的 `works.card_id` 作为兼容字段，并让它表示列表第一项。

优点是能直接查询引用关系、稳定阻止删除、支持排序和未来扩展角色卡配置；旧数据可以无损迁移。代价是后端需要同步维护兼容字段和关联表。

### 方案 B：在 `works` 中保存 `card_ids` JSON 数组

实现较快，但删除保护和引用查询必须解析所有剧本 JSON，难以利用数据库约束，也不利于后续增加顺序之外的角色配置。

### 方案 C：把角色卡内容复制进剧本

会破坏角色卡复用和统一编辑语义，不采用。

## 数据模型与迁移

### `works`

新增：

- `player_attributes TEXT NOT NULL DEFAULT '{}'`：剧本级玩家初始属性字典。

保留：

- `card_id`：旧客户端兼容字段，始终等于有序角色卡列表第一项或 `NULL`。

新增关联表：

```sql
CREATE TABLE IF NOT EXISTS work_cards (
    work_id INTEGER NOT NULL REFERENCES works(id) ON DELETE CASCADE,
    card_id INTEGER NOT NULL REFERENCES cards(id) ON DELETE RESTRICT,
    position INTEGER NOT NULL,
    PRIMARY KEY (work_id, card_id),
    UNIQUE (work_id, position)
);
```

数据库初始化时执行无损迁移：

1. 确保 `works.player_attributes` 和 `work_cards` 存在。
2. 对没有关联记录但 `works.card_id` 非空的旧剧本，插入 `position = 0` 的关联记录。
3. 对 `player_attributes` 为空的旧剧本，从其第一张角色卡的旧 `initial_state.attributes` 复制一份；已有剧本级属性不覆盖。
4. 对重复启动保持幂等，不重复插入关联或覆盖已有玩家属性。

角色卡旧的 `initial_state.attributes` 字段保留在角色卡数据中，以兼容旧导入和旧会话，但新角色卡编辑器不再展示或主动管理该字段。

### API 形状

`WorkCreate` 和 `WorkUpdate` 新增可选字段：

```python
card_ids: Optional[list[int]] = None
player_attributes: Optional[dict] = None
```

兼容规则：

- 新客户端发送 `card_ids` 时，以它为准；服务端去重并保留顺序。
- 旧客户端只发送 `card_id` 时，转换成零项或一项 `card_ids`。
- 更新时显式 `card_ids: []` 或 `card_id: null` 都会清空角色卡引用；未提交字段不改变已有列表。
- 所有非空卡 ID 必须存在，否则返回现有风格的校验错误。

作品响应增加：

- `card_ids`：有序 ID 列表。
- `cards`：按顺序返回的角色卡摘要/详情列表。
- `player_attributes`：剧本级玩家属性。

同时继续返回 `card_id` 和 `card`，分别对应第一张角色卡，保证旧前端和旧接口调用不立即失效。

### 会话快照

新增 `conversations.card_snapshots TEXT NOT NULL DEFAULT '[]'` JSON 数组。每个新会话在创建事务中保存当前有序角色卡列表的深拷贝；继续填充旧的 `card_snapshot` 为第一张角色卡，以兼容旧消费者。

迁移规则：非空 `card_snapshots` 不覆盖；旧的非空 `card_snapshot` 转为单元素数组。读取角色卡时优先使用非空数组，即使 `card_id` 后来为空或对应角色卡已删除。

新会话的 `current_state.attributes` 从创建时的 `work.player_attributes` 复制，剧本后续修改玩家属性只影响之后新开的会话。

## 后端行为

### 角色卡引用与删除

引用查询改为通过 `work_cards` 聚合剧本；兼容查询仍合并旧 `works.card_id` 中尚未迁移的记录。删除检查、引用列表和实际删除在同一个 `BEGIN IMMEDIATE` 事务中执行。存在任意引用时返回现有 HTTP 409 结构，包含剧本 ID 和名称。

### AI 上下文

`repositories.get_conversation_cards(conversation)` 返回快照数组；空数组才回退到当前剧本的角色卡列表。`adventure_engine.build_messages` 为每张角色卡生成独立的角色信息段，并保留每张卡的名称、人格、性格、说话方式、固定指令、关系和剧情角色属性。角色卡顺序与剧本列表一致。

无角色卡时不生成角色信息段，保持现有无卡剧本行为。

## 前端行为

### 角色卡编辑器

- 移除玩家属性动态编辑区。
- 保留角色卡自身的角色属性、固定指令、文字关系和其他角色字段。
- 保存已有卡时保留隐藏旧 `initial_state` 数据，不让表单删除关系或未知字段。

### 剧本设置

增加“玩家初始属性”区，使用现有动态属性行能力保存到 `player_attributes`。

增加“剧本角色卡”有序列表：

- 从独立角色卡库选择并添加角色卡。
- 显示每张卡的名称和性格/人设摘要。
- 支持移除、上移、下移。
- 不允许同一剧本重复添加同一张卡。
- 允许列表为空。

保存剧本时只提交 `card_ids`、`player_attributes` 和剧本/世界书字段，不创建或更新角色卡。

### 会话与离线模式

- Mock 作品迁移 `card_id` 为 `card_ids`，并把旧角色卡 `initial_state.attributes` 复制到作品 `player_attributes`（仅当作品尚无该字段）。
- Mock 新会话深拷贝所有当前角色卡到 `card_snapshots`；旧会话只使用自己的非空快照。
- 冒险页按快照数组展示/使用多张角色卡；角色修正默认文本合并当前会话快照中的相关角色信息。
- 角色卡库的引用计数、编辑提示和删除检查覆盖全部分页数据。

## 错误处理与兼容性

- 无效角色卡 ID：创建/更新剧本返回校验错误，前端保留表单内容并提示。
- 删除竞态：前端预检查只用于体验，后端事务检查是最终保护。
- 旧剧本：继续读取单 `card_id`，初始化迁移后作为一项列表。
- 旧会话：继续读取单 `card_snapshot`，迁移为单元素数组；快照优先于实时角色卡。
- 旧离线数据：从嵌入作品卡和旧 `card_id` 派生独立卡库、角色卡列表和剧本玩家属性。

## 明确不在范围内

- 不增加初始数值关系编辑器。
- 不为每张角色卡单独设置玩家属性。
- 不复制角色卡内容到剧本中作为新的独立资源。
- 不改变已经开始的会话的角色卡快照或玩家初始状态。

## 验收标准

1. 角色卡编辑器中没有玩家属性设置区。
2. 剧本设置中可以编辑并保存玩家初始属性。
3. 一个剧本可以按顺序添加、移除和调整多张角色卡。
4. 新会话使用该剧本当时的全部角色卡和玩家属性；旧会话不变。
5. 同一角色卡可以复用到多个剧本，任何仍被引用的卡都不能删除。
6. 旧单卡剧本、旧单卡会话和离线数据都能迁移并继续使用。
7. 后端和前端全量测试、语法检查、启动检查通过。
